# 任务导航调度系统 —— 快速理解架构文档

版本:2026-09-17(「方案一」:行进纯 VIO 不建图 + 锚定专用同步 tracker)

---

## 1. 系统总览:三个进程、三个终端

| 进程 | 启动方式 | 职责 | 观察终端 |
|---|---|---|---|
| **调度器** task_nav_scheduler.py | `./run_task_nav.sh`(本终端) | 状态机编排、到达判定、定位触发、优雅关停 | 本终端(`[TASK]` 行 + 指令输入) |
| **cuvslam** run_vio_tasknav.py | 调度器 fork 管道子进程 | VIO 位姿源(行进) + 地图锚定(定位) | SLAM 观察窗口(tail 日志,原地刷新面板) |
| **NavSide** run_nav.py --real | 调度器弹 gnome-terminal 窗口 | SRU 深度策略推理 + 速度指令输出 | 交互终端窗口(面板 + A/S/D/F/G 按键,最高优先级) |

相机分工:CPC8763000MZ(B)= cuvslam 被动双目(激光关);CPC8763000J0(A)= NavSide 深度。

## 2. 数据流

```
相机B IR 848x480@10 ──→ cuvslam track() ──→ odom 增量 ──→ pub_pose(全局系)
                                        └──→ [SCHED] pose=(x,y,z,q..) t=.. 文件通道(10Hz)
调度器 tail slam_sched 文件 ──→ XZ 距离 ≤ 容差持续 1s ──→ VIO 到达判定
cuvslam pub_pose ──OpenCV→Z-up──→ UDP 127.0.0.1:8082 ──→ NavSide RobotComm ──→ pos_w(机器人状态)
调度器 ──NAVSIDE_CMD_FILE──→ NavSide(goal x y z / A/S/D/F / quit,低优先级)
NavSide ──NAVSIDE_SCHED_FILE──→ 调度器([SCHED] mode=.. zero_reason=.. 状态行;按键优先级最高)
cuvslam ──SLAM_SCHED_FILE──→ 调度器(anchor=busy/ok/fail、pose 流、note=诊断)
```

## 3. 调度器状态机

```
BOOT ──SLAM 就绪──→ WAIT_STARTUP_ANCHOR（cuvslam 首帧自动锚定）
  └─ busy → ANCHORING ── ok ──→ start_segment(0) → SEGMENT（resume VIO + 下发 goal + S）
SEGMENT ──VIO 位姿 ≤ arrive_tolerance 持续 arrive_confirm_s──→ arrive()：
  先 nav "A"（停推理+清 LSTM+发零）→ 再 slam "pause"（关 VIO）→ ARRIVED 提示
ARRIVED ──用户 localize（转发给 cuvslam）──→ ANCHORING ── ok 且偏差 ≤ 容差 ──→ 下一段
全部任务点完成 → DONE → 两端优雅退出
```

容错:SLAM 意外崩溃 → 10s 延迟自动重启(相机 USB 复位)→ 启动锚定续接当前任务点,上限 3 次。

## 4. 核心设计决策(为什么这样改,含实证)

### 4.1 行进 = 纯 VIO 不建图(方案一)
- **现象**:全同步 SLAM 时,后端内联工作(回环/PGO/关键帧优化)饿死采集线程 → 行进位姿流卡顿 0.5s~125s;禁回环无效(根因是整图优化)。
- **做法**:行进 tracker `slam_cfg=None`(track 只跑 VIO 前端:特征帧间跟踪 + IMU 融合,输出 odom);段内全局位姿 = 锚定位姿 ⊕ odom 帧间增量(pub_pose)。
- **依据**:定位层与建图层在 cuVSLAM 里解耦;锚定读磁盘参考图、与活动图无关。

### 4.2 锚定 = 专用同步 tracker + 预热
- **GIL 崩溃**(绑定层 bug):async 模式下 localize_in_map 回调从后台 SLAM 线程触发,某回调位点缺 `nb::gil_scoped_acquire` → `Fatal Python error: PyThreadState_Get` 随机硬崩。sync 模式下回调在主线程(持 GIL)同步执行 → 根治。
- **z=7 定位失败**:根因**未定论**。「全新 tracker 重力/姿态未初始化导致投影错误」仅为假设之一(启动点同样用全新 tracker 却能成功);预热是辅助措施,不能认定能解决第二点失败。
- **做法**:锚定时经共享 holder 创建同步 tracker;相机线程预热(连续取帧 track,仅统计跟踪成功的帧,期间 IMU 不暂停),拿到有效帧后自行挂起采集并交付,主线程用**同一帧、同一时间戳**执行 localize;定位完销毁、切回纯 VIO。与稳定重定位的 `Desktop/run_vio-小推车.py`「先跟踪后定位」行为对齐。

### 4.3 定位搜索参数
- 三级由粗到细:coarse 25m/1.0m/0.15rad → mid 4m/0.5m/0.06 → fine 1m/0.2m/0.03(与经典 localize 模式完全一致;曾用 10m/5m 半径导致「同位置 localize 模式能定位、tasknav 不能」)。
- **猜测位姿 = pub_pose 的 XZ、Y=0,姿态 = 单位四元数**:「Y 漂移是第二点失败根因」的证据不足(第一点成功时 Y 也已漂 0.51m);当前更可信的假设是**累积姿态的滚转/俯仰漂移把搜索网格带斜**(底层 T_candidate = T_guess × T_offset)——单位姿态不注入漂移,航向由 360° 角向搜索覆盖,零损失。待「同帧分别用 last-pose guess 与新 guess」的对照实验定论。

### 4.4 到达与停机顺序
- 到达判定:调度器用 VIO 实时位姿(不依赖 NavSide 机器人状态);
- 停机顺序:**先 nav "A"(停推理)→ 0.5s → 再 slam "pause"**(关 VIO 后状态源冻结,必须先停稳推理);
- `apply_sched_line` 曾漏赋值 `self._mode`(调度器命令全是空操作,按键 F 后调度器的 A 停不掉推理)——已修。

## 5. 文件通道协议

| 通道 | 方向 | 内容 |
|---|---|---|
| NAVSIDE_CMD_FILE | 调度器→NavSide | `goal x y z` / `A` / `S` / `D` / `F` / `quit`(追加行) |
| NAVSIDE_SCHED_FILE | NavSide→调度器 | `[SCHED] mode=.. run_policy=.. zero_reason=.. goal_dist=..`;退出写 `process=exit` |
| SLAM_SCHED_FILE | cuvslam→调度器 | `[SCHED] anchor=busy/ok/fail`、`pose=(x,y,z,qx,qy,qz,qw) t=<epoch>`(10Hz)、`paused=0/1`、`note=<诊断文本>` |

优先级:NavSide 终端按键(A/S/D/F/G)永远最高——按键置 `user_override`,调度器的 S/D 行进指令被忽略,直到调度器发 A 交还。

## 6. 诊断体系(排查工具,打包时保留)

- `analyze_slam_log.py`:位姿流空洞分析(按 anchor/paused/walk 分阶段)+ 掉帧警告交叉验证;
- cuvslam 侧:`[localize] FAILED <err>` 直落日志;诊断行(当前位姿+锚定帧特征数)与 `[diag]` 计时埋点(track/viz/主循环整轮 >2s)经 `note=` 通道**直接显示在调度器终端**;
- 判读:特征数 <30 = 视图纹理不足(转朝向);位姿可信且特征正常仍失败 = 地图覆盖/坐标系问题。

## 8. 已知问题 / 上游事项

1. **绑定层 GIL 缺陷**(已绕开):async 回调缺 GIL 保护 → 定位强制走同步 tracker。上游修法见 `cuvslam_上游问题总结.md`;
2. **Orbbec USB 栈失稳**:快速开关相机会致设备掉总线/标定取帧失败(重启延迟 10s + 开相机重试 15s 缓解);
3. 相机 B 无 1280x720 深度流(USB 降速),深度只给相机 A;
4. 每次进程退出有 nanobind 引用泄漏(不影响运行);
5. 行进段偶发 1~2s 位姿流空洞(埋点待定位,嫌疑:渲染/IO 抖动;频率已大幅低于旧版)。
