## 1. 离线检查与选点（不启动相机）

首次测试先在图上选 1–2 个直道目标，起始位置与第一个目标应明显超过 1 m 到达阈值。不要一开始选整圈，也不要把机器人起点作为第一个任务目标。

```bash
./run_task_nav.sh --pick-only
```

操作：深绿色内部按目标顺序左键；Z 撤销，C 清空，滚轮缩放，中键拖动，Enter 保存，Esc 取消。保存到 `config/task_points_selected.json`。

```bash
./run_task_nav.sh --check-only
```

通过标准：定位数据库指纹匹配、目标数量/坐标与所选一致，最后提示“仅选点/检查完成”。这只校验地图和目标，**没有实际启动定位，也不能预先保证当前位置的 A* 起点可通行**。

若报没有选点文件，返回选点；若地图指纹不匹配，核对 `ref_map`、`astar.map_package` 和源 `data.mdb`，重新生成/选点，不能手改 JSON 指纹跳过校验。

可选软件基线检查：

```bash
.venv_navside/bin/python -m unittest discover -s tests -p 'test_*.py' -v
```

当前完整基线为 33 项通过，运行时不连接机器人。配置/代码自上次验证后有修改再执行；不要反复重跑来代替观察现场现象。

## 2. SRU 关闭：检查启动定位、路径和打印

把机器人置于参考地图覆盖、现场确认可走的位置并保持静止，然后执行：

```bash
./run_task_nav.sh --no-sru --task-points-file config/task_points_selected.json
```

预期顺序：SLAM 就绪 → 自动重定位 → A* → 显示 15 点 → 恢复 VIO → SEGMENT。只应有调度器终端和 SLAM 观察窗口，不应新开 NavSide 推理窗口或占用下游深度相机。

检查并记录：

- 调度器显示 `SRU OFF`；输入 `status` 能看到状态、任务点和 anchor_seq。
- SLAM 面板有完整 01/15 到 15/15，全部 `Y=0.000000`。
- 01 点的 XZ 等于本次重定位 XZ；15 点等于当前目标 XZ。
- 路径转角沿可通行区域绕行，不跨越黄线对应的虚拟墙；参考点与连线均通过碰撞检查。
- `route.json` 中 `includes_start=true`、`includes_goal=true`、`reference_count=15`，`scheduler.sent_to_sru=false`。
- 关闭模式不生成 `segment_delivery.json` / `delivery_events.jsonl`，也不等待 ready/running。

可以原地停留确认定位是否跳变；原地检查不要求机器人自动移动。若 A* 失败，查看同次运行的 `failures.jsonl`。起点越界/落入不可通行区域时先核对实际定位，不把它自动移动到另一格；调整到可定位位置后输入 `localize`，应仍规划第一个目标。

## 3. SRU 关闭：验证多段和中途暂停

使用独立遥控沿真实走廊移向当前目标。进入 1 m 范围并持续 1 s 后，应提示 VIO 到达、状态 ARRIVED，VIO 暂停。此模式不会替遥控器停车，现场停稳后输入：

```text
localize
```

通过标准：新重定位成功并通过偏差校验后，任务点推进一个；下一段 01 点来自新定位，而不是上一个目标的固定坐标。最后一个目标到达后仍需要 `localize` 确认，全部任务结束。

另开一轮，用同一组选点测试中途恢复：在到达之前先通过遥控停车，调度器输入：

```text
pause
status
localize
```

通过标准：先进入 PAUSED；重定位后段号/当前目标不变，anchor_seq 增加，起点和参考点刷新。暂停不能被当作到达，也不能直接跳到下一个目标。

如果只想反复验证同一段定位/路径，也使用 `pause` → 停稳 → `localize`，不要用 `force` 模拟完成。`force` 只能跳过实际 ARRIVED 后成功定位的偏差校验，不能绕过 A* 失败。

## 4. SRU 关闭：可选的重启恢复验证

先保持静止，在已有活动段时从调度器输入：

```text
send slam q
```

这是受控退出 SLAM，用来观察意外进程退出后的调度恢复，不模拟所有真实崩溃原因。预期旧参考点清除 → RESTART_WAIT → 约 10 秒后新 SLAM 启动 → 新定位 → 同一未完成目标重新规划。

通过标准：任务点下标不推进；新日志为 `slam_r...`，新 anchor_seq、新结果目录；不会继续使用旧路径。只需做一次，不连续快速重启相机。测试通过后 `quit` 退出本轮。

## 5. 开启 SRU：先测试短直道单段

先 `quit` 结束关闭模式。需要改变目标时重新 `--pick-only`，第一次开 SRU 只留一个直道目标。确认机器人可以开始行进后执行：

```bash
./run_task_nav.sh --sru --task-points-file config/task_points_selected.json
```

应出现 NavSide 推理窗口和深度预览。观察完整链路：

```text
anchor=ok → A* 成功/SLAM 15 行
→ segment_load → path=ready
→ SLAM resume → segment_start → path=running
→ S/LOW_SPEED 行进 → ARRIVED → 停稳后 localize → 完成
```

通过标准：

- 段文件中的 `path_w` 为 15×3，Z 全部 0.5；`goal_w` 的 Z 为 0.695。
- `path_w` 的水平坐标等于参考点 `(地图Z,-地图X)`，最后一点水平位置等于最终目标。
- ready/running 的 session_id 和 segment_id 属于本轮本段；不是旧日志里的确认。
- 深度画面有有效距离，机器人初始朝向和地图/路径关系合理；观察是否仍持续向右偏。
- `logs/real_*.csv` 中 `final_vx/final_wz` 与实际方向一致；同时记录 `goal_dist`、`zero_reason`、`depth_valid_pct`。
- 到达后停住，重定位确认最终任务，正常退出。

当前没有单独的“SRU 只推理不发速度”测试开关；如需这种额外模式，应先实现后再用，不能把现有 F/A 或 `--no-sru` 当成该模式。

## 6. 开启 SRU：验证人工停车再恢复

另开一轮短直道，在到达前在 **NavSide 交互终端**按 A 或 F 停车（按窗口提示提交）。调度器应显示 PAUSED。机器人静止后，在**调度器终端**输入 `localize`。

通过标准：目标不变，重新定位/规划；新 segment_id；重新 ready → running 后才行进。人工停车后直接按 S/D 不能恢复旧路径。正常行进时 S/D 只切换速度模式。

调度器 `pause` 也可暂停；实时人工停车优先使用 NavSide 交互终端按键。SLAM 的 tail 观察窗口不负责接收这些指令。

## 7. 转角与多段回廊

直道与暂停恢复都正常后，逐级增加难度，每次重新选点、检查、记录：

1. 一个转角的一段路线，观察路径方向、机器人转向与黄线距离。
2. 两个目标，验证到点重定位后第二段的起点/目标更新。
3. 左上转角、右上转角分别验证；最后才测试完整长方形回廊。

每次只改变一类参数；不要同时调整地图边界、VAE、裁剪和频率。地图连续可走不等于 SRU 一定精确跟随参考折线。发生持续偏右时先停车保存日志，检查地图坐标变换、实际姿态、路径交付和模型输入，再判断是否是模型训练问题。

## 8. 根据现象定位问题

| 现象 | 优先检查 | 查看哪里 |
|---|---|---|
| `--check-only` 就失败 | 地图名/数据库/选点指纹、目标是否可通行 | 调度器输出、map.json、task_points_selected.json |
| OFF 模式一直等待启动定位 | SLAM 相机、参考地图是否覆盖、重定位结果 | slam_*.log、slam_sched_*.log；初次自动定位失败后才手动 localize |
| OFF 模式起点错误或突然跳变 | 定位坐标/姿态、现场与地图对应关系 | 原始 anchor、实时 pose、route.json.start_xy |
| OFF 模式 A* 失败 | 起终点、自由区接缝、膨胀后通道、转角预算 | failures.jsonl、审核地图、独立 A* |
| OFF 模式无法到达/推进 | 最新 VIO 是否更新、距离与持续时间、是否已 localize | status、slam_sched_*.log 的 pose 和 t |
| 中途停车后跳到下一目标 | 段状态与人工停车事件 | status、nav_sched_*.log、对应段目录；这是调度问题 |
| ON 等待 ready 超时 | 下游启动、模型/深度相机、原 RobotComm.load_task 的 API 等待 | NavSide 窗口原始异常、nav_cmd/nav_sched；ready 默认 60 s |
| ready 有，running 没有 | 恢复 VIO 后是否收到新 UDP 位姿，端口配置和时效 | SLAM 事件、nav_deploy.yaml、nav_sched；running 默认 10 s |
| 旧版 `pose_stale_or_invalid` | 下游位姿超时/异常，不是墙体厚度判断 | 新版已细分以下等待、恢复和异常事件 |
| `waiting_pose` / `WAIT_POSE` | 已零速等待，保留原目标和路径 | 包龄 `pose_age_s`；等待期间 VIO 继续，不需要手动 resume |
| `pose_resumed` | 稳定恢复，继续同一段 | `wait_s` / `stable_samples`；段 ID 和参考点应不变 |
| `pose_timeout/jump/invalid/sequence_reset_requires_localize` | 长断流、位姿突变、非法数据或序号倒退 | `nav_sched_*.log` / `delivery_events.jsonl`；停稳后 `localize` |
| `waiting_pose reason=inference_pose_expired` | 推理结束时旧位姿已过期，丢弃当次输出并等待 | NavSide 推理时间、SLAM 更新间隔；稳定恢复后继续原段 |
| `depth_unavailable` | 下游相机、USB、串号、深度读取错误 | NavSide 窗口、深度预览 |
| `inference_failed` | 模型输入形状、15 点、裁剪尺寸、ONNX 异常 | NavSide 窗口异常堆栈、segment_delivery.json |
| 有 running 但速度始终 0 | 到点阈值、行走阈值、暂停/零速原因 | CSV zero_reason、goal_dist、final_vx/final_wz |
| OFF 正常、ON 后卡顿/偏右 | 交付/坐标、深度、策略、双相机 USB/计算资源竞争 | 同时对照 route、delivery_events、CSV 和现场录像 |

NavSide 终端原始 traceback 当前不自动保存为独立完整 stdout 日志；错误时及时复制终端内容。机器状态通道和 CSV 已落盘，不要只保留一张路径截图。

位姿等待恢复的参数、现场观察顺序和协议限制见[2026-09-30 更新说明](位姿等待恢复_测试说明_20260930.md)。本次 55 项离线测试通过；等待期间人工 A/F/G 或 `pause` 仍必须 `localize`，不能作为短时断流恢复测试。
