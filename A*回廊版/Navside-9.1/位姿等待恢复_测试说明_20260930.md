# 位姿短时断流：等待与恢复（2026-09-30）

后续实测发现旧帧追赶与累计偏移误判，已补充修复；最新证据、上游改动及复测方式见[位姿积压修复与复测](位姿积压修复与复测_20260930.md)。下方参数已同步，文末 55 项验证是初版历史记录；最新为 70 项离线测试。

`pose_stale_or_invalid` 来自下游位姿检查，不是 A* 判定墙太厚。墙线、障碍区或膨胀导致的问题会表现为起点/终点不可通行、无路等规划错误，应分别排查。

## 当前行为

| 情况 | 行为 |
|---|---|
| 实际接收的新位姿超过 1 秒未更新 | 发零速，进入 `WAIT_POSE`；保留当前目标、段号和 15 点，SLAM/VIO 继续运行 |
| 连续稳定收到有效新位姿，且通过连续性检查 | 自动继续原段，清空旧推理记忆和动作，再用恢复后的位姿推理；不重新规划、不推进目标 |
| 等待超时、位置/姿态突变、序号/接收时间倒退、非法数据 | 保持停车，调度器进入 `PLAN_FAILED`；静止后输入 `localize`，以新定位重新规划当前目标 |
| NavSide 人工 A/F/G 或调度器 `pause` | 保持停车，必须 `localize`；收到新位姿或按 S/D 不会自动恢复 |
| SLAM 崩溃 | 保留原来的延迟重启及重新定位流程，继续未完成目标；不会自动恢复旧路径 |

短时等待时 **不要输入 `pause`**，否则会按人工停车处理。想提前结束等待、改为手动重定位：在调度器依次输入 `pause`，停稳后 `localize`。

## 参数

在 `config/nav_pathaware.yaml` 的 `policy` 下修改，重启调度器生效；原版 `nav.yaml` 独立。

| 参数 | 当前值 | 含义 |
|---|---|---|
| `state_max_age_s` | 1.0 秒 | 真实位姿接收时间超过此值，先零速等待 |
| `pose_recovery.timeout_s` | 5.0 秒 | 等待恢复上限；从最后有效包算起断流总时长最多约 6 秒；晚到的新包不能解除已超时的停车 |
| `pose_recovery.stable_s` | 0.6 秒 | 恢复阶段新包须连续稳定的时间 |
| `pose_recovery.min_samples` | 3 | 恢复阶段至少观察到的不同新位姿数，同时满足稳定时间；反复读缓存不计数 |
| `pose_recovery.max_sample_gap_s` | 0.3 秒 | 恢复阶段相邻采样间隔、包龄上限；超出则重新累计稳定时间，等待截止时间不延后 |
| `pose_recovery.max_position_jump_m` | 1.0 米 | 非跨断流的相邻位姿变化上限；跨断流累计比较另加进入等待前的模式限速×时间容差，进入等待时固定 |
| `pose_recovery.max_rotation_jump_deg` | 60 度 | 相邻有效位姿、等待前后姿态角差上限；四元数正负号翻转不算姿态改变 |
| `pose_recovery.stable_position_span_m` | 0.15 米 | 恢复窗口内位置跨度上限；超过则重新累计稳定时间，防止旧帧仍在追赶就恢复 |
| `pose_recovery.stable_rotation_span_deg` | 10 度 | 恢复窗口内姿态角差上限 |

以上为本次初始配置，尚未现场验证。`5 Hz`、15 点包含首尾、模型路径 Z=0.5、SLAM 打印 Y=0 均保持原约定。

**坐标系检查的边界**：现有 UDP 包没有源坐标系/重定位编号。本版用段会话、SLAM 重定位/退出事件、接收序号/时间及位置/姿态连续性约束恢复。运行或等待期间收到重定位事件会停止旧段；细小且连续的坐标系变化仍无法仅凭现有包格式严格识别。本版没有声称通过坐标系 ID 验证；若后续需要严格识别，需让上游传输坐标系代次。

## 启动与观察

先在旧调度器输入 `quit`，确认旧进程退出，再运行：

```bash
cd /home/amov/navside_real/NavSide_log/Navside-9.1
./run_task_nav.sh --check-only
./run_task_nav.sh --sru --task-points-file config/task_points_selected.json
```

1. 调度器先显示路径 `ready/running`。正常推理频率仍为 5 Hz。
2. 短时位姿中断应显示“第 N 段等待位姿：已发零速，保留当前目标和 15 点路径”。此时 `status` 为 `WAIT_POSE`，NavSide 面板 `path: waiting_pose`、命令全零，SLAM 15 点继续显示。
3. 稳定恢复后显示“位姿连续有效，自动继续原目标和原路径”；段 ID、任务序号和参考点不变。
4. 超时/异常出现 `requires_localize`，保持停车；之后恢复的数据不会自行启动。输入 `localize` 后重新定位、规划到同一个未完成目标。
5. 单独验证人工 A/F/G 或 `pause`：必须保持停止，直到 `localize`。不要将人工 `pause` 当作短时断流测试。

先观察现场自然出现的断流；本次没有提供会向机器人注入异常位姿或主动切断真实通信的命令。断流、非法数据等注入在下面的离线测试中完成。

## 日志判读

`logs/task_nav/nav_sched_*.log` 和每段的 `delivery_events.jsonl` 会记录：

```text
path=waiting_pose ... reason=pose_stale pose_age_s=1.0... pose_sequence=...
path=pose_resumed ... reason=pose_stable wait_s=... stable_samples=...
path=error ... reason=pose_timeout_requires_localize ...
```

其他原因：`pose_jump_requires_localize`、`pose_invalid_requires_localize`、`pose_sequence_reset_requires_localize`。突变事件附 `position_jump_m` / `rotation_jump_deg`、`jump_reference`（`pre_wait_pose` 或 `previous_sample`）、`reference_sequence`、`sample_dt_s`、`position_limit_m`。等待事件附 `before_zero_s`、`motion_allowance_m`、`wait_position_limit_m`。推理期间使用的位姿过期会记录 `waiting_pose reason=inference_pose_expired`，丢弃那次输出后等待稳定恢复。

原现场日志 `/home/amov/Desktop/test.txt` 的 4 次 `pose_stale_or_invalid` 前均已规划并开始运行。对应上游事件间隔约 1.12～1.51 秒，但上游事件可能打印缓存，不能把该间隔当成准确 UDP 包龄；新版事件补充了真实接收包龄。
