## 正常导航时打开诊断

退出旧调度器及其子进程，再在调度器终端执行：

```bash
cd /home/amov/navside_real/NavSide_log/Navside-9.1
python3 scripts/pose_diagnostics.py prepare
source logs/pose_diag/enable_latest.sh
./run_task_nav.sh --sru --task-points-file config/task_points_selected.json
```

`prepare` 只创建本轮目录和配置快照。必须在**同一个终端**执行 `source` 和启动命令。已运行的进程不会因 `source` 自动启用诊断。

另开终端观察实际接收坐标、相机时间戳、源序号、接收间隔、包龄、SRU 取样序号和段状态：

```bash
cd /home/amov/navside_real/NavSide_log/Navside-9.1
python3 scripts/pose_diagnostics.py watch --latest
```

观察脚本按 `Ctrl+C` 只退出观察并生成报告，**不停止机器人**。机器人仍用原 NavSide A/F/G 或调度器 `pause` 停车。

测试结束，在调度器输入 `quit`，等两端退出后生成完整报告：

```bash
python3 scripts/pose_diagnostics.py report --latest
```

报告默认在 `logs/pose_diag/run_时间/`。指定旧轮次：

```bash
python3 scripts/pose_diagnostics.py report --dir logs/pose_diag/run_实际时间
```

**普通启动后能否生成本轮诊断，取决于启动终端是否仍有诊断环境变量。** 同一终端之前 `source` 过，可能继续写入旧目录；新终端没有 `source`，通常不采集诊断。`report --latest` 只分析最近准备的目录，不会补采刚结束的普通运行。为避免混淆，每轮都重新执行 `prepare → source → 启动`，并核对报告页首的采集时间。

关闭诊断，在下次启动前执行：

```bash
unset NAV_POSE_DIAG_DIR NAV_POSE_DIAG_MODULE
```

## 建议先做的对照

先做 **SRU 关闭、机器人在现场保持静止约 30 秒** 的 VIO 对照，再做短距离运动对照。每个对照重新 `prepare` 和 `source`，分别保存：

```bash
python3 scripts/pose_diagnostics.py prepare
source logs/pose_diag/enable_latest.sh
./run_task_nav.sh --no-sru --task-points-file config/task_points_selected.json
```

此时只运行上游/规划，不启动下游，所以没有 RX/SRU 数据是正常现象；`watch` 会显示原始 VIO。等待启动定位、规划、恢复 VIO 后，再观察静止段。`--no-sru` 不控制底盘，保持静止依靠现场操作者。结束输入 `quit`，生成报告查看 `vio_frames.csv`。

随后按上一节开启 SRU 做短段测试，记录出现异常时机器人是否移动、转动，以及开始/停稳时间。不要只用“零速指令”代替实际静止参考。一次只改变一个测试条件；先查清静止 VIO 是否稳定，再比较行走震动、图像特征、IMU 与图像时间间隔、深度显示/推理负载的影响。

原“主线程新建、相机仍用旧 tracker”的缺陷已修复：现在由相机线程创建/切换，成功、失败和取消都会完成交接并清空旧基线。旧日志的 `main_tracker_created` 仍按历史规则分析；新日志改看 `tracker_switched` 和每帧 `vio.tracker_generation` / `tracker_id`。

新报告第 3 节会列出“代次 / 切换时刻 / 已核对 VIO 帧数 / 对象不一致帧数”：恢复跟踪后应有帧且不一致为 0。某代 0 帧只代表尚无跟踪证据，例如定位后还在暂停，不能直接判定切换失败。代次 0 为启动，之后每次交接递增，失败/取消也递增；不能跨代比较局部 VIO 坐标来判定跳变。

分析器已自动排除跨 tracker 代次的局部位移，此处 CSV 留空，`local_frame_continuous=false`；全局出口位移仍单独检查。旧数据若无代次字段则用已记录的 tracker ID 辅助识别切换，两个字段都缺失时无法识别该边界。

`imu_frame_rejected` 的 `reason` 表示图像被跳过：`imu_not_fresh` 是最多等 150 ms 仍无距图像不超过 20 ms 的先行 IMU；`image_behind_imu` 是图像落后已缓存最新 IMU 超过 250 ms；`image_timestamp_not_increasing` 是图像时间不递增；`cancelled` 表示定位请求或退出取消本次处理。启动/切换时少量拒绝不等于故障，持续出现应查采集/积压与时钟。拒绝计数是图像数，不是丢失的 IMU 样本数。

`vio_frames.csv → track_s` 是调用墙钟耗时，`track_cpu_s` 只计当前调用线程的 CPU 时间；两者相差大可能涉及等待或线程调度，不能单凭相减认定 GPU 或 GIL 是根因。`imu_wait_and_register_s` 分离 IMU 等待/注册，`stereo_timestamp_delta_s` 给出左右图像设备时间差。原始 `imu_capture` 记录 SDK 等待区间，供继续定位采集停顿。

## 如何区分问题

| 观察结果 | 优先排查 |
|---|---|
| 原始 VIO 已跳变；出口、接收、SRU 数值一致 | VIO 输入/跟踪，重点看特征数、IMU 迟到/缺失、图像与 IMU 时序；第二次 42 m 异常已有此方向证据 |
| 原始 VIO 连续，全局出口突变 | 锚定后的位姿累积与坐标变换；不要跨重定位代次当作普通相邻帧 |
| 相机时间间隔正常，SDK/track/发送间隔突然变大 | 上游卡顿或源数据积压；查看 `preprocessing_and_imu_s`、`track_s`、`queue_age_s`、可视化耗时 |
| 发送持续正常，接收变慢或集中到达 | 用户态接收调度、内核 UDP 队列或传输环节 |
| 接收持续正常，SRU 输入包龄/推理耗时变大 | 主循环/深度/推理阻塞；`inference_pose_expired` 可以出现“最新包很新、推理用的旧包已超时” |
| 接收包与 SRU XY/四元数不一致 | 缓存或状态组装逻辑；Z 固定为 0.695 是现有设计，不按它报错 |

相机 `source_timestamp_ns` 是设备时钟，不能直接减 UTC 或主机单调时间。主机同一次启动的单调时钟用于发送→接收→推理比较，程序用 boot ID 检查时钟是否可比。`timestamp_sec` 仍是旧接口的状态读取时间，诊断将它明确记为 `state_read_timestamp_sec`，不把它当作相机采样时间。

`send_to_receive_s` 包含内核排队和接收线程调度，并不是纯网络延迟。SDK 取帧时间也不是光学曝光时间，SDK 内部缓冲仍要通过源时间与取帧间隔对照分析。缺失记录可能来自启动先后、强杀或诊断日志丢行；报告不会自动把它们叫作 UDP 丢包。

## 实现、兼容及验证

当前上游 38 项、下游 85 项离线测试通过，包含交接和新版报告的验证；证据在 `logs/vio_center_fix_20260930/`。下面的 76 项及“只调整报告”属于此前诊断工具阶段，不能用来描述现在的运行代码。新 VIO/居中规划尚需实机复测。

诊断脚本本身只读写文件，不绑定 SRU 端口，不发送机器人指令。真实接收线程和推理调用处有可选记录钩子，因此采集的是实际使用的数据。

未启用诊断时保持原 `<7d>` 56 字节包。启用后，在同一个数据报末尾附加 `PTD1` 诊断信息（总长 124 字节），包括发送进程 UUID、递增序号、源时间、取帧/完成/发送时间、锚定代次；位姿前 56 字节不变。新版接收器同时支持两种格式。**必须同时重启本机新版上下游；旧版接收器不支持诊断包。** 这些新元数据只用于记录分析，不用于改写停车/恢复判断。

后台队列写盘，满队列时丢诊断行并累计计数；不让日志写盘阻塞控制主线程。IMU 记录会增加日志体积，适合分轮短时诊断；正常退出更利于日志完整。强杀仍可能丢尾部记录。
